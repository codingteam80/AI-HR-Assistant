# AI HR Assistant Developer Guide

## Layer flow

```text
UI Page
  ↓
Service
  ↓
Repository
  ↓
SQLAlchemy Model / Database
```

### UI

The UI displays data and collects user input. It should not contain SQL
queries or complex business rules.

### Service

The service validates business rules and coordinates multiple repositories.

### Repository

The repository owns database queries and CRUD operations.

### Model

The model defines database tables, columns, relationships, and constraints.

### Schema

Pydantic schemas validate data before it reaches the service layer.

## Company isolation

Most HR records contain `company_id`.

Queries must include the current company ID so one company cannot read
another company's users, employees, departments, roles, leave records, or
documents.

## Employee identity

Do not use the employee's full name as a unique identifier.

Use:

```text
company_id + employee_number
```

Multiple employees may legally share the same full name.

## Passwords

Never store or log a plain-text password.

The application stores only the Argon2 hash generated by:

```text
authentication/password_manager.py
```

## Initial data

The seed script is safe to run multiple times:

```powershell
python scripts\create_initial_data.py
```

It checks existing records before creating:

- Company
- System roles
- Initial administrator
- Administrator employee profile

## Debugging order

When a feature fails, check the layers in this order:

1. `.env` and `config/settings.py`
2. Database connection and tables
3. Model relationships and constraints
4. Repository query
5. Service validation
6. UI page or component
7. Streamlit session state

## Authentication flow

```text
Login Form
  ↓
Pydantic LoginRequest
  ↓
AuthService
  ↓
CompanyRepository + UserRepository
  ↓
Argon2 verification
  ↓
AuthenticatedUser
  ↓
AuthSessionManager
  ↓
Admin or Employee Layout
```

Security rules:

- Login is always scoped by company code.
- Username or email is searched only inside that company.
- Passwords and hashes never enter Streamlit session state.
- Inactive companies, users, and roles cannot log in.
- Initial accounts must replace the temporary password.
- Admin layouts repeat authorization checks for defense in depth.


## User and employee management flow

```text
Admin Employees Page
  ↓
EmployeeAccountCreate schema
  ↓
AdminManagementService
  ↓
Company-scoped repositories and services
  ↓
User and Employee database records
```

Rules:
- Employee number is unique inside one company.
- Full name is not a unique identifier.
- Optional accounts are linked through user_id.
- New accounts must change their temporary password.
- Roles and lists are filtered by company_id.
- The current administrator cannot deactivate itself.


## Organization setup flow

```text
Admin Company/Department/Role Page
  ↓
Pydantic organization schema
  ↓
OrganizationService
  ↓
Company/Department/Role Repository
  ↓
Company-scoped database record
```

Rules:

- Company code is immutable after creation.
- Company display name may be updated.
- Department names and codes are unique inside one company.
- The same department name may exist in another company.
- System roles are protected from deactivation.
- Custom roles may be created per company.
- Roles assigned to users cannot be deactivated.


## Persistent theme selection

```text
Theme toggle
  ↓
Streamlit session_state
  ↓
URL ?theme=light|dark
  ↓
Browser localStorage
```

- Form/widget reruns use session state.
- Browser refresh uses the URL query parameter.
- A new Streamlit session uses the last browser localStorage value.
- Logout does not clear the selected theme.
- Only `light` or `dark` is stored in browser storage.


## Simplified default-account reset flow

```text
Default admin login
  ↓
AuthenticatedUser.must_change_password
  ↓
app.py blocks protected routing
  ↓
Mandatory password-change page
  ↓
AuthService.change_password()
  ↓
must_change_password=False
  ↓
Normal portal access
```

`create_initial_data.py` sets the flag only when the initial administrator
is first created. `require_default_password_reset.py` explicitly sets the
flag for an existing default account without changing its current password.


## Signed-cookie refresh authentication

```text
Successful credential login
  ↓
Signed timestamped cookie issued
  ↓
Full browser refresh
  ↓
st.context.cookies reads cookie synchronously
  ↓
Signature, age, password fingerprint, account, company, and role validated
  ↓
AuthenticatedUser restored to session_state
```

No password is stored in the cookie. The cookie is invalidated when the
password hash changes. A configured `AUTH_COOKIE_SECRET` is required for
cookies to remain valid across Streamlit server restarts.


## Form-widget contrast selectors

Streamlit does not render all form controls using the same DOM structure.
`st.text_input`, `st.date_input`, and `st.selectbox` therefore require
different selectors. `theme_loader.py` contains both high-specificity CSS
and a MutationObserver fallback for:

- `stTextInput`
- `stNumberInput`
- `stDateInput`
- `stTimeInput`
- `stTextArea`
- `stSelectbox`
- `stMultiSelect`


## Employee-only authorization flow

```text
Employee credentials
  ↓
role_name = employee
  ↓
mandatory password change when temporary
  ↓
Employee Portal
```

Protection layers:

1. Employee sidebar shows Admin Portal only when `AccessControl.is_admin()`.
2. `app.py` changes unauthorized admin navigation back to employee mode.
3. `admin_layout.py` calls `AccessControl.require_admin()` independently.
4. Signed-cookie restoration reads the current database role and does not
   store or elevate permissions in browser state.


## Login/logout transition rule

Cookie components must be allowed to mount before the app changes route.
The current implementation uses `st.fragment(run_every="1s")`, followed by
`st.rerun(scope="app")`. Do not use iframe `location.replace()` for the
main Streamlit application.


## HR Policy Q&A flow

```text
Admin Policies Page
  ↓
PolicyCreateRequest
  ↓
PolicyService
  ↓
PolicyRepository
  ↓
hr_policies table
```

```text
Employee Question
  ↓
PolicyAssistant
  ↓
Published/effective company policies only
  ↓
Generic title/summary/heading/section scoring
  ↓
Direct extracted answer + policy sources
```

Rules:

- No external knowledge is used.
- Only `published` policies are searchable.
- Future-effective policies are excluded.
- Every query is filtered by `company_id`.
- The same title/version may exist in another company.
- The same title/version cannot repeat inside one company.
- Unknown questions return the exact fallback message.

## Secure password-reset architecture

```text
Forgot Password page
  ↓
PasswordResetService
  ↓
company + registered Login Email lookup
  ↓
password_reset_tokens (SHA-256 hash only)
  ↓
EmailSender adapter
  ├─ LocalOutboxEmailSender
  └─ SmtpEmailSender
```

Reset completion:

```text
Raw token from email
  ↓
SHA-256 lookup + expiry/single-use validation
  ↓
Argon2 new password hash
  ↓
token used_at
  ↓
old signed-cookie fingerprint invalid
```

The raw reset token is present only in the email URL. Never write it to the
database, application logs, audit messages, or public UI.


## Real SMTP delivery verification

```text
.env SMTP settings
  ↓
EmailIntegrationService.get_status()
  ↓
Admin → Integrations
  ↓
Send Internet Test Email
  ↓
SmtpEmailSender
  ↓
SMTP provider over the network
```

The status check does not make a network request. The test-email action is
the explicit network and authentication verification.

Never expose `SMTP_PASSWORD` in Streamlit widgets, tables, exceptions,
application logs, or test output.


## Email-only password recovery

```text
Email input
  ↓
UserRepository.list_by_email_for_password_reset()
  ↓
zero, one, or multiple active tenant accounts
  ↓
one independently hashed token per account
  ↓
company-labeled reset email
```

The reset token record stores `company_id` and `user_id`, so Company Code is
not required in the public request form.

## Chat Assistant terminal diagnostics (v0.8.8.217)

`modules/smart_ai/terminal_trace.py` provides request-local terminal-only
retrieval diagnostics. `SmartPortalAssistant` creates one trace per request and
passes it into `HybridRetriever`; no trace object is stored in Streamlit Session
State, returned in `HRAssistantResponse`, or rendered by either Chat page.

When enabled, the trace exposes bounded, already-authorized evidence only and
prints to stderr. It includes file-stage and chunk-stage BM25/vector/hybrid
scores, selected files/chunks, final Qwen evidence, deterministic/router output,
model timing/retry events, raw Qwen output, and the final normalized answer.

Keep this diagnostic path side-effect free: it must never change ranking,
permission scoping, prompt content, retry count, or UI state. Disable it with
`SMART_AI_TERMINAL_DEBUG_ENABLED=false` when console traces are not needed.

## Chat Assistant terminal candidate-answer diagnostics (v0.8.8.218)

v0.8.8.218 extends the existing terminal-only trace with source-labeled candidate answer excerpts. Set `SMART_AI_TERMINAL_DEBUG_CANDIDATE_ANSWER_CHARS` to bound each candidate excerpt. Candidate diagnostics are observational only: they are not stored in Session State, returned in `HRAssistantResponse`, or used as an extra ranking/generation signal. The trace also prints router and Qwen answer options plus the selected final answer path for easier FAIL/PARTIAL diagnosis.

## v8.8.219 Chat Assistant diagnostics and relevance hardening

- Base: exact v8.8.218 package.
- Terminal-only retrieval trace is structured for human debugging and mirrored to per-request files in `logs/chat_assistant/`.
- Trace/log output may contain authorized HR/policy evidence for the current request; keep the project/log folder access-controlled like the rest of the local HR data.
- Log file failures are fail-safe and do not alter the answer path.
- Relevance/no-match guard rejects a mathematically nearest chunk when its specific topic anchors do not sufficiently match the question.
- Existing out-of-scope behavior (e.g. unrelated general-knowledge questions) remains in place.
- PolicyService adds the same topic-support check before accepting deterministic policy search matches, covering the preflight/Ollama-unavailable path.
- Streamlit displays one top approved policy source only; internal evidence selection and terminal diagnostics can still use/show multiple supporting chunks.
- No special broad-topic `COVERAGE` retrieval mode is present in this checkpoint.
- PDF/DOCX extraction, company/role isolation, BM25/vector/RRF architecture, chunk sizes/overlap, and unrelated HR workflows are intentionally retained.


## v8.8.220 compact terminal / full-log diagnostic contract

- Base: exact v8.8.219 package.
- Normal runtime with `SMART_AI_TERMINAL_DEBUG_LOG_ENABLED=true`: keep stderr
  compact and human-scannable; preserve the full retrieval/generation evidence
  in one request-local `logs/chat_assistant/chat_trace_*.log` file.
- Compact stderr must show retrieval totals, selected source scores/chunk counts,
  up to three candidate-answer scores, final answer/source, and runtime status.
- Full log must retain detailed BM25/vector/hybrid stages, excerpts, final
  evidence, relevance decision, router/Qwen options, top-nearest source, and
  request summary.
- If the log path cannot be opened or writing fails, diagnostics must remain
  fail-safe and the terminal may fall back to verbose output rather than lose
  evidence.
- Diagnostic formatting must never change ranking, prompt content, answer
  normalization, retry count, tenant/role scoping, Streamlit state, or visible
  source-selection behavior.
